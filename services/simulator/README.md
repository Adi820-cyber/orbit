# Orbit live hospital simulator

A separate service that **acts as a hospital**. It signs in to the ERP as an admin account (and optionally one desk account per hospital) and does what the people there would do, around the clock, through the same ERP API the web app uses:

- punches staff in and out of their rostered shifts (some late, some absent, a few forget to punch out);
- fixes missed punches the next morning through a correction, which an admin reviews after a human-like delay;
- plans rosters ahead, renews expiring doctor credentials, and, on an empty hospital, hires staff and builds a service catalogue;
- registers patients, opens visits (outpatient, emergency, day-care, inpatient), records the services delivered by the right kind of person, and closes visits when they are over.

Decisions and limits: [ADR 0017](../../docs/decisions/0017-live-hospital-simulator.md). How it fits the deployment: [DEPLOYMENT.md](../../docs/orbit/DEPLOYMENT.md).

> **Everything it creates is simulated.** The people, patients and visits are fictional and generated by rules. They are not real hospital data, and the product still labels every ERP screen as illustrative. Do not present them as real.

## What it needs

1. The ERP API deployed with `erp` in `ORBIT_LIVE_SOURCES` (a combined deployment, or the separate hospital-operations one).
2. The database to have the migrations, the organization seed (`0001`) and the **reference** seed (`0008`: departments, specialties, shift patterns, settings, services). People and activity seeds (`0009`, `0010`) are **not** needed: the simulator creates those. If they are already loaded it carries on from them and never hires over existing staff.
3. An admin account in Supabase Auth with an operator membership. Optional: a desk account for each hospital.

## Run it on your computer

```
cp services/simulator/.env.example services/simulator/.env   # then fill it in
npm run start:local --workspace=@orbit/simulator             # runs until Ctrl+C
npm run tick --workspace=@orbit/simulator                    # one tick, then exit
```

Stopping it is the only off switch needed. Nothing it did is undone, and starting it again carries on from whatever time it is then.

## Configuration

Everything is an environment variable. A bad value stops the process at startup and names the variable, never its value. Secrets are never logged. Full list with defaults: [.env.example](.env.example).

| Variable | Meaning | Default |
|---|---|---|
| `ERP_API_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | Where to act | required |
| `SIM_ADMIN_EMAIL`, `SIM_ADMIN_PASSWORD` | The admin account | required |
| `SIM_DESK_<HOSPITAL>_EMAIL` / `_PASSWORD` | A desk account for one hospital | none (the admin serves it) |
| `SIM_FACILITIES` | Hospitals to act on (`avenhurst,brackmoor`) | every hospital the admin sees |
| `SIM_TICK_SECONDS` | Seconds between ticks | `60` |
| `SIM_VISITS_PER_STAFF_PER_DAY` | Patient volume | `0.6` |
| `SIM_ABSENT_RATE`, `SIM_LATE_RATE`, `SIM_MISSING_OUT_RATE`, `SIM_EARLY_EXIT_RATE` | How often each happens (each at most 0.5) | `0.03`, `0.06`, `0.03`, `0.02` |
| `SIM_BOOTSTRAP` | Hire staff and build a catalogue on an empty hospital | `true` |
| `SIM_PAUSED` | Read and plan, write nothing | `false` |
| `SIM_MAX_WRITES_PER_TICK` | Most writes in one tick | `60` |
| `SIM_CATCHUP_SECONDS`, `SIM_CATCHUP_MAX_HOURS` | How late is still "now", and how far back it may fill in | `300`, `24` |
| `SIM_SEED` | Same seed, same people doing the same things on the same days | `orbit-sim` |
| `SIM_GROQ_KEYS`, `SIM_OPENROUTER_KEYS`, `SIM_OPENROUTER_MODEL`, `SIM_DIRECTOR_MINUTES` | The optional day director | none, `60` |

## How it behaves

**It keeps no schedule.** Each tick reads the hospitals' current state from the ERP and does whatever *should have happened by now*. Every decision (who is late, how long a visit lasts, which services it needs) comes from a seeded random stream keyed on the person, visit and date, and every write carries an idempotency key from the same labels. So a tick is safe to repeat, skip or run after a long pause, and a restart never changes a plan or records anything twice.

**After downtime** it catches up. A punch only a few minutes late is recorded by the desk at the real time, exactly as a person pressing the button would. Anything later is back-dated by the admin to when it should have happened (the API allows an admin to back-date up to 31 days; the simulator stops at `SIM_CATCHUP_MAX_HOURS`, 24 by default, and never rewrites older history).

**It can only do what its accounts can.** It acts through the API as real operator accounts; role and facility come from the login, never from a request. The admin never decides a correction it requested itself (the API enforces the four-eyes rule). With no desk account for a hospital, a forgotten punch-out is recorded by the admin directly instead of through a correction.

**The day director** (optional). About once an hour a language model is asked what kind of hour each hospital is having: a surge at one, staff off sick at another. It returns a small structured "mood", validated against a schema and clamped to a range, naming only hospitals it was given. It never touches a record. With no key, or every provider failing, the day is ordinary. Keys are tried in order, a rate-limited or rejected key is parked, and no key is ever logged. The request holds no personal or clinical data.

## Safety rails

- `SIM_PAUSED=true` stops all writes without stopping the process; `SIM_MAX_WRITES_PER_TICK` bounds a tick.
- One failing hospital or record is logged and skipped; it never stops the others. Repeated tick failures back off up to five minutes.
- Only `https` API URLs are accepted (plain `http` only for localhost).
- A rule refusing a write (an expired credential, a service not offered) is never retried.

## Host it on Render or Railway

Vercel cannot run this: its functions are short-lived and its scheduled jobs are too limited for a process that acts all day. Render and Railway run an ordinary always-on Node process.

The install is tiny (zod and the shared contracts; no TypeScript or test tooling, because Node runs the `.ts` files directly), about 8 MB in a few seconds. The commands, run from the **repository root**:

| | |
|---|---|
| Build | `npm ci --omit=dev --ignore-scripts --workspace=@orbit/simulator` |
| Start | `node services/simulator/src/main.ts` |
| Node | 22 (the repository requires `>=22.18 <23`, and `npm` refuses to install on anything else) |

**Render.** A Blueprint is in [render.yaml](../../render.yaml): a background worker with those commands and `NODE_VERSION=22`. In the dashboard choose *New → Blueprint*, point it at the repository, and fill in the prompted values. A worker is a paid instance type on Render, as far as I know; check current pricing. (A free *web service* spins down when idle, which would stop the simulator.)

**Railway.** Create a service from the repository, leave the root directory empty, set the Build and Start commands above and the variables from `.env.example`. Railway normally reads the Node version from `engines`; if your service uses another version, set the one your builder documents. Set `PORT` only if you want the health endpoint probed (it is provided automatically).

**Both:** use **strong passwords** for the admin and desk accounts, not the demo ones, and enter them in the host's secret settings. A health endpoint (`GET /` or `/health`, JSON) is served only when `PORT` is set.

### How much load it puts on the API

Each tick costs about three reads per hospital plus whatever it writes, so a 60-second tick is roughly:

| Hospitals | Reads per month at 60 s |
|---|---|
| 1 | about 0.15 million |
| 6 | about 0.9 million |

If the API is on a serverless plan with a monthly request allowance, lengthen `SIM_TICK_SECONDS` (120 halves it) or limit `SIM_FACILITIES`. Each write also adds an audit row, so at six hospitals expect roughly two thousand new rows a day. That is an estimate and has not been measured on Supabase; there is no automatic cleanup.

## Tests

```
npm test --workspace=@orbit/simulator       # 95 tests, no network
npm run typecheck --workspace=@orbit/simulator
```

The tests run the engine against an in-memory ERP typed from the real contracts, including a full simulated hospital day, catch-up after downtime, restart safety, failure isolation and the write budget.

## Not verified

- Render and Railway themselves (the commands were run from a clean copy of the repository on Windows with a production-only install; the Blueprint was not run on Render).
- The model providers (the director is tested against scripted responses, never a real Groq or OpenRouter call).
- A run lasting days, and stopping on the hosts' termination signal.
- Against the hosted Supabase project and the deployed API: all real-API runs so far were against a local copy of the API and database, signing in to the real Supabase Auth.
